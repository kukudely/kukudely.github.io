让编程 Agent 修复一个测试，用户可能只需要输入一句话。接下来，Agent 却要读取项目约定、查找源码、执行命令、修改文件，再根据测试结果继续调整。每一步都会产生新的上下文。

任务执行得越久，模型下一次需要承接的内容就越多。即使用户没有继续发消息，连续的工具调用也可能让上下文接近容量上限。

Codex 将这件事拆成了几个相互配合的环节：组装当前请求、估计上下文占用、判断窗口何时需要切换、生成压缩结果，以及安装和保存新的历史。理解这条链路，有助于回答一个实际问题：**Agent 怎样在有限的上下文窗口内持续工作，同时保留任务目标、用户约束和已经取得的进展？**

本文围绕 2026 年 10 月的实现展开，源码链接固定到官方仓库提交 `970111f6cb62cc02fe36a82ea7d71b37a2889c97`。具体路径受模型、provider 能力和功能开关影响。

## 会话记录与模型上下文各自承担什么职责

理解压缩之前，需要区分三个层次。

| 层次 | 保存或表达的内容 | 压缩时发生的变化 |
| --- | --- | --- |
| 会话记录，也称 rollout | 消息、工具事件、配置和检查点等持久化记录 | 追加压缩检查点，旧记录可以继续存在 |
| 当前有效上下文 | 下一次推理需要承接的历史状态 | 用压缩后的内容替换相应历史 |
| 单次模型请求 | 按模型协议编码的输入、指令、工具和输出要求 | 根据当前模型与运行状态重新构造 |

假设一个任务已经产生了上百次工具调用，磁盘仍然可以保存这些操作的记录。压缩后，下一次推理承接的内容可能缩减为：

```text
基础指令与当前环境
按策略保留的原始消息
压缩结果
压缩后新增的消息与工具输出
```

因此，在界面或日志中能找到旧消息，只能说明记录仍然存在。模型当下是否逐字看到它，还要看当前有效上下文。

这种分层也为恢复会话提供了基础。持久化记录负责保留执行过程，模型上下文则围绕后续推理的需要组织内容，两者可以采用不同的数据保留策略。

## 一次请求如何从历史中组装出来

最小 Agent 常用一个 `messages` 数组保存对话。随着工具和多模态能力增加，仅用角色加文本描述历史就会遇到限制。

Codex 的 `Prompt.input` 使用 `Vec<ResponseItem>`，可以容纳普通消息、工具调用、工具结果、推理相关条目和压缩条目。`Prompt` 还保存基础指令、工具规格、并行调用开关和输出 schema。可以从 [Prompt 的定义](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/client_common.rs)看到这些组成部分。

这意味着，上下文成本涉及模型可见的多种输入。只统计聊天文字，会漏掉工具 schema、大段命令输出或图片等内容。

### 用户回合中还包含多次模型采样

一次“修复测试”的请求，可能经历下面的过程：

```text
用户提出任务
  → 模型决定读取文件
  → 工具返回源码
  → 模型决定修改实现
  → 工具返回编辑结果
  → 模型决定运行测试
  → 工具返回测试输出
  → 模型给出结论
```

Codex 为单次采样维护 `StepContext`，其中包含模型设置、环境快照和工具路由等状态。工具路由将本次请求公开的工具与后续调用的执行环境关联起来。

基础上下文与任务进展也有不同的维护方式。开发者指令和环境状态可以在新窗口中重新构造，用户消息、模型输出和工具结果则持续积累到历史中。工作目录或运行环境变化时，重新构造的上下文能够反映当前状态，减少对旧摘要中环境描述的依赖。

此外，工具声明支持增量表达。在对应模式下，声明可以通过历史条目提供，顶层 `tools` 字段因而可能为空。分析请求时，需要结合历史中的声明和当前协议模式一起判断。

## 当前上下文占用与累计消耗

假设连续三次模型请求，每次输入都约为 50,000 tokens。这三次输入合计约为 150,000 tokens，当前窗口的占用仍应根据下一次请求承接的内容计算。

这两个指标回答不同的问题：

- **当前上下文占用**：下一次推理需要容纳多少内容？
- **累计消耗**：任务运行至今，一共使用了多少资源？

压缩完成后，当前上下文占用可以下降，累计消耗则可能继续增加，因为生成摘要本身也会调用模型。

### 用服务端反馈校准本地估算

Codex 会结合最近一次响应的 usage 与本地新增内容，估计当前占用。其主线可以简化为：

```text
当前占用估计
≈ 最近一次响应的 total_tokens
  + 最近模型条目之后新增内容的估计
  + 按服务端计数语义补计的历史推理成本
```

最后一项取决于相关成本是否已经包含在服务端反馈中，处理时需要避免重复计数。具体逻辑见 [ContextManager 的用量计算](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/context_manager/history.rs)。

为什么仍然需要本地估算？因为模型返回后，工具可能又输出了几千行日志，用户也可能追加要求。这些内容尚未进入下一次模型请求，最近的 usage 无法反映它们。

下面是一个省略推理补计的示例：

| 项目 | Token 数 |
| --- | ---: |
| 最近响应提供的用量锚点 | 70,000 |
| 随后新增的工具输出估计 | 8,000 |
| 随后新增的用户消息估计 | 2,000 |
| 当前占用估计 | 80,000 |

本地计算采用按内容字节数估算等启发式方法。它适合辅助预算判断，但精度受语言、内容类型和模型分词方式影响。外层 JSON 转义和传输元数据，也应与模型实际看到的内容区分开。

## 压缩阈值如何参与 Agent 循环

压缩判断同时涉及模型窗口、自动压缩阈值和有效窗口上限。

在参考实现中，模型已知上下文窗口为 `C` 时，模型信息层的自动阈值最多取 `floor(0.9 × C)`；如果显式配置了更低的值，则取较低值。最终是否触发，还取决于统计范围与运行模式。

### 两种统计范围

| 范围 | 比较对象 | 适合怎样理解 |
| --- | --- | --- |
| `Total` | 当前活跃上下文的总占用 | 整个窗口已经使用多少 |
| `BodyAfterPrefix` | 当前占用减去窗口的 prefill 基线 | 带入前缀之后又增长了多少 |

例如，新窗口的基础上下文、保留消息和压缩结果组成了 40,000 tokens 的前缀。随后又增加 30,000 tokens，两个范围对应的数值分别是 70,000 和 30,000。

只统计新增部分时，完整窗口仍然受独立上限约束：

```text
有效完整窗口上限
= 解析后的上下文窗口 × effective_context_window_percent / 100
```

达到范围内的自动阈值，或达到有效完整窗口上限，都可能触发切换。特定 TokenBudget 配置还会影响 fallback buffer 的处理。这些判断集中在 [上下文窗口预算逻辑](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/context_window.rs)中。

因此，不能仅凭一个 90% 的数字推断所有客户端的实际压缩时机。

### 检查点分布在执行过程的多个位置

Codex 会在采样之前检查预算，也会在工具结果进入历史、准备继续调用模型时检查。配置相应阈值后，还可以在回合结束时处理压缩；模型切换和手动操作也有对应入口。

这个安排直接对应长任务的特点：同一个用户回合中，工具输出就可能让上下文迅速增长。预算检查必须覆盖 Agent 循环内部，才能在下一次推理前及时腾出空间。

## 三条上下文切换路径

Codex 的自动压缩流程会根据功能模式和 provider 能力选择不同路径。主要分支可以概括为：

```text
需要压缩或切换窗口
  ├─ 启用 TokenBudget → 进入新窗口流程，跳过摘要生成
  ├─ provider 支持远端 V2 → 请求服务端生成压缩条目
  └─ 其他情况 → 客户端组织模型调用，生成文本摘要
```

分派入口位于 [run_auto_compact 所在的回合逻辑](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/turn.rs)。

### 客户端组织文本摘要

源码中的 local compaction 由客户端构造摘要提示，并调用所配置的模型完成摘要。这里的 local 描述流程组织方式，模型仍然可以运行在远端。

完成后，客户端将摘要、按策略保留的用户消息和重新构造的基础上下文组合起来。参考实现为保留的用户消息设置了约 20,000 tokens 的预算；整个新窗口还包含其他部分。

这种路径的结果容易阅读，但摘要质量依赖模型能否保留任务目标、明确约束、已验证结论和剩余工作。

### 服务端返回压缩条目

远端 V2 路径在输入尾部加入 `compaction_trigger` 控制项，通过 Responses 流式调用获取压缩结果。

服务端返回的 `compaction` 条目包含 `encrypted_content`。客户端负责保存并继续传递这个不透明状态，无法直接从中阅读普通文本摘要。

接收过程还会检查完成事件、流式错误和压缩条目数量。只有恰好收到一个符合要求的压缩条目，并确认响应正常完成，结果才具备被采用的条件。相关实现见 [远端 V2 压缩流程](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/compact_remote_v2.rs)。

### TokenBudget 开启新窗口

启用 TokenBudget 时，流程会跳过模型摘要和服务端摘要，进入专门的新窗口处理逻辑。跨窗口承接哪些状态，由这一模式的保留机制决定。

这也说明，出现 `ContextCompaction` 生命周期事件，只能证明进入了相应流程；具体是否调用摘要模型，还需要看实际分支。

在工具可用的配置下，模型还可以通过 `get_context_remaining` 查询剩余预算，通过 `new_context` 请求新窗口。客户端会在后续执行边界处理请求。窗口切换与工作目录、文件等执行环境分别管理。

## Codex 内部协议与公开压缩 API

为自己的 Agent 接入压缩时，需要确认目标服务提供哪一种接口。

| 方式 | 触发方式 | 入口 |
| --- | --- | --- |
| 公开 API 的服务端自动压缩 | 服务端依据请求中的阈值判断 | `/responses` 携带 `context_management` 和 `compact_threshold` |
| 公开 API 的独立压缩 | 客户端主动调用 | `/responses/compact` |
| 本文讨论的 Codex 远端 V2 | 客户端按预算或后台策略启动 | Responses 输入中加入 `compaction_trigger` |

公开独立压缩接口返回的是后续应承接的完整窗口，其中可能同时包含保留条目和加密压缩条目。调用方应将返回窗口整体传入后续请求，保持其内容完整。具体用法见 [OpenAI Compaction 文档](https://developers.openai.com/api/docs/guides/compaction)。

“兼容 OpenAI”仍然需要细化到具体能力。一个服务能够处理 Chat Completions，并不能据此推断它支持 Responses 或 Codex 的内部压缩控制项。接入时，应以目标服务的接口契约为准。

## 新窗口怎样承接旧任务

压缩结果只是新上下文的一部分。远端 V2 还会筛选原始消息、施加保留预算，并重建基础上下文。

其中，真实用户输入、HookPrompt、部分 Agent 间消息，以及特定开关下的客户端工具输出或 developer 消息，会按各自规则处理。消息来源和内容类型都会影响保留结果，仅看 `role` 不足以判断。

参考实现对远端显式保留消息设置了 `64_000` tokens 的预算。该预算约束这部分原始内容，压缩条目和新窗口总长度需要分别考虑；图片也有单独的预算处理。

可以用下面的结构理解它们的关系，具体插入顺序由实现决定：

```text
新上下文
  = 重建的基础上下文
  + 按类型与预算保留的原始消息
  + 压缩条目
  + 压缩期间新增的尾部内容（如有）
```

部分原始消息保留精确表达，压缩条目承接更长历史中的状态。两者配合，既控制窗口大小，也为继续执行任务保留必要信息。

### 后台压缩要处理并发更新

同步压缩需要让后续推理等待。源码还提供了可选的异步压缩机制：先捕获历史快照，在后台生成候选结果，让前台继续推进。它要求启用 `AsyncCompaction`、未启用 `TokenBudget`，并且 provider 支持远端 V2；启动时还会检查其他运行条件。

考虑这样一段时间线：

```text
t0  当前历史：A B C D
t1  后台开始压缩 A B C D
t2  工具返回新结果 E
t3  用户追加要求 F
t4  后台返回压缩候选 S
```

采用结果时，新的历史需要保留 `E F`：

```text
S 所代表的压缩后前缀 + E F
```

如果直接用后台结果覆盖当前全部历史，新增工具结果和用户要求都会丢失。

Codex 因此会检查历史代际、前缀边界和认证代际，并保留快照之后的 suffix。普通追加与历史替换具有不同含义：前者允许继续拼接新增内容，压缩、回滚等替换操作则可能使候选过期。模型身份和压缩兼容信息也参与安装校验。

后台请求完成后，候选仍需通过这些检查才能生效。相关安装与历史替换逻辑位于 [会话实现](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/mod.rs)。

## 压缩后的会话如何恢复

只替换内存中的历史，无法解决程序重启后的恢复问题。Codex 还会把压缩后的替代历史和相关恢复信息写入 rollout 检查点。

两种视角下的数据结构可以表示为：

```text
磁盘记录
原始事件 → 压缩检查点 → 新消息 → 新工具结果

恢复后的有效上下文
检查点中的 replacement_history → 后续有效记录
```

恢复过程识别检查点，并结合后续记录重建状态。回滚、分支和回合边界还需要额外处理，入口可参阅 [rollout 恢复逻辑](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/rollout_reconstruction.rs)。

这让长任务可以在恢复后承接压缩窗口，避免重新装入已经被替代的全部旧历史。不过，检查点机制与完整的事务保证仍需分别分析；仅有持久化调用，无法证明写入失败时一定会回滚内存变更。

## 从这些机制设计自己的 Agent

实现最小 Agent 时，可以先建立一条可验证的同步流程，再逐步增加能力。

### 先把预算检查放到正确位置

分别维护当前上下文占用与累计消耗，将工具定义、新工具输出和其他模型可见内容纳入预算。至少在发送请求之前，以及工具执行完、准备继续请求模型之前检查。

为下一次输出和估算误差留出空间。等到窗口已经严重超限时才生成摘要，摘要请求本身也可能容纳不下输入。

### 用结构化交接信息约束摘要

摘要可以围绕任务继续执行所需的信息组织：

```text
当前目标与用户约束
已经做出的决定
已完成的改动
已验证的事实与测试结果
尚未完成的工作
关键文件和定位信息
失败过的尝试及原因
下一步行动
```

保留一段近期完整交互，有助于承接正在进行的工具调用。截断与替换时，应维护工具调用和结果的配对关系，避免留下孤立的调用或输出。

采用摘要前，可以检查空内容、输出截断状态、新窗口长度和协议结构。语义是否遗漏仍需要通过实际任务检验，例如压缩后能否遵守用户限制、区分验证结果与猜测，以及继续尚未完成的工作。

### 让压缩结果可以持久化和重放

保存原始事件，同时记录替代历史检查点。恢复时从检查点承接后续事件，并明确处理持久化失败的行为。

同步版本稳定之后，再考虑后台生成候选。后台化需要增加历史版本、压缩边界、模型兼容性和尾部保留等机制，收益主要体现在等待时间，代价则是更复杂的状态管理。

服务端原生压缩也应通过能力判断接入。将普通文本摘要、公开 Responses 压缩和特定协议支持分别建模，能够让兼容性问题更容易定位。

最终，压缩质量要回到任务本身衡量：模型是否记得约束、是否承接已有结论、是否减少重复劳动，以及能否把剩余工作做完。Token 数量说明节省了多少空间，任务表现才说明这些空间换来了怎样的连续工作能力。
